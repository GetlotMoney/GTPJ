先从 Git 的四个基本东西看

把它们当成“照片”和“书签”，就不会再被名字绕晕。

Commit（提交）= 一张代码快照例如 2f5fa5e，内容一旦形成就不会自己变化。
Branch（分支）= 可移动书签它指向某个提交；继续提交时，书签会向前移动。
Tag（标签）= 固定书签用来给正式框架或母版定名；按规范创建后不再移动。
PR（合并请求）= 待审搬运单它只是请求把一条分支的提交合入 main；草稿状态不会自动合并。

完整正确结构：管理、框架、母版、实验四层分开

下面每一层负责不同的事。纵向是“谁登记谁”，不是代码自动继承；横向的 V1、V2、V3、V5 是平级正式框架。

Tag 的作用：它只告诉你“这张代码快照叫什么”。Tag 不会把那张快照复制进 main，也不会因为数量多就改变模型。

到底什么会污染？

这里的“污染”指：错误代码进入正式管理线或母版，导致后续实验从不干净的起点继续。

动作会污染吗普通话解释正确做法
旧分支继续存在不会只是多一个可回看的书签；主要问题是列表显得乱。先标历史，再单独做分支清理审计。
旧 Tag 继续存在不会只是固定指向旧快照；它不会自己进入 main。保留并写清“正式、母版、Trial、历史特殊项”。
合并错误实验代码到母版会以后每项实验都会从带旧实验改动的底稿开始。实验代码永不并回 framework/vX-template-vN。
实验 B 从实验 A 分支继续开会B 会偷偷带上 A 的代码，无法判断到底谁起作用。A、B 都从同一个准确母版 commit 独立开。
只把实验结果账本合入 main不会只更新参数、日志引用和结论，不改变母版代码。先检查 diff 只含账本和文档。
移动或重建正式 Tag会破坏追踪同一个名字突然指到另一张代码快照，旧实验无法复现。正式 Tag 创建后永不移动。
确认后的创新建立 V6规范执行时不会它成为平级新框架，不回头改 V5。新建 framework/v6、v6 和独立 V6 母版。
现在直接合并 PR #2需先审核分支数量不会污染，但 120 个提交的文件改动范围很大。保持草稿，先审 origin/main..PR头部 的内容边界。

我建议的安全处理顺序

先把唯一入口定稳，再处理历史枝叶；不要在同一次操作里同时迁移管理体系和删除旧分支。

先保持 PR #2 为草稿。现在不合并，避免在还没看清 120 个提交内容边界时移动 GitHub main。
审核“会进入 main 的文件”。重点看工作流、台账、文档、模型、配置、训练入口分别改了什么；分支名数量不作为判断依据。
确认新的唯一管理入口。让 GitHub main 只承担总管理；正式模型框架、母版、实验代码继续保持各自分支边界。
单独同步必要引用。PR 合并不会上传本地 framework/* 分支和 model/v5-template-v1 Tag；是否上传要另列清单再执行。
最后才整理旧分支。把旧 codex/*、dev/*、promote/* 分成“必须保留历史”和“可删除远端书签”两类；删除前先证明提交仍能由 Tag、main 历史或归档引用找到。

一句话收口：你的老分支和 Tag 可以作为历史证据继续存在；新管理体系放进 main；只有确认后的新模型才升级成平级正式框架分支。这样既不丢历史，也不会无限嵌套，更不会让实验代码互相叠加。
