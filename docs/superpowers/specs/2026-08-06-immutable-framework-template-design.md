# GTPJ 正式框架只读母版统一设计

```yaml
design_id: SYS-WORKFLOW-V5-DESIGN
status: proposed
date: 2026-08-06
scope: 正式框架母版、四类实验起点、旧实验映射、V5 瘦身
supersedes_rule: 新实验直接从可继续修改的 framework/vX 长期分支起步
does_not_rewrite: 历史 Tag、旧 Trial/Attempt、运行证据、已有成绩
```

## 1. 结论

每个正式框架都必须有一份独立、干净、冻结的代码母版。母版只用来复制，不直接改。该框架下面的调参、消融、创新、确认四类实验，都必须从同一个母版 Tag 和同一个母版提交独立开工，不能从另一个实验继续叠代码。

创新实验成功后，不把代码并回旧母版。先把成功代码清理、确认并冻结，再注册成一个新的同级正式框架；新框架拥有自己的新母版和四类实验。这样既保留 V1、V2、V3、V5 的历史来源连线，也不会形成目录套娃或代码越叠越长。

## 2. 现在要解决的问题

当前规则已经把正式框架整理成同级，也给每个框架分了四类实验，但“实验从哪一份代码开始”还不够严格：

1. `framework/vX` 既像正式框架代码，又可能继续接收修改，容易把母版和开发线混在一起。
2. 如果第二个实验接着第一个实验的代码做，两个实验就不再只差一个动作，后面无法判断效果来自哪里。
3. V5 从 V3 演变而来，代码里仍可能保留旧参数别名、兼容分支、废弃入口和后续实验代码；继续在这份代码上加开关，只会越来越长。
4. 旧 `Trial / Attempt` 中有真实证据，不能删除；但如果继续把它们当成新实验入口，人就很难看懂一个实验到底有多少次运行、调了哪些参数。

## 3. 四个对象必须分开

| 对象 | 人话解释 | 例子 |
|---|---|---|
| 正式框架 | 已经被接纳的一套方法身份 | `FRAMEWORK-V5` |
| 框架母版 | 该正式框架可复制、不可修改的干净代码快照 | `MODEL-V5-TEMPLATE-V1` |
| 实验项 | 基于母版回答一个具体问题 | `V5-ABLATION-001` |
| 实际运行 | 实验参数表里真正跑的一行 | `RUN-003` |

Git 身份同时记全：

```text
正式框架：FRAMEWORK-V5
母版编号：MODEL-V5-TEMPLATE-V1
冻结 Tag：model/v5-template-v1
准确提交：40 位 Git commit
实验分支：exp/v5/ablation/v5-ablation-001-local-branch-effect
```

母版编号与框架编号不能混用。`FRAMEWORK-V5` 表示方法身份；`MODEL-V5-TEMPLATE-V1` 表示这套方法的第一份干净代码母版。以后如果只修复不改变方法含义的母版缺陷，新增 `MODEL-V5-TEMPLATE-V2`，旧母版仍然保留。如果修改会改变方法行为，就不能继续叫 V5，必须先作为创新实验验证，成功后再成为新的正式框架。

## 4. 选用的做法

比较过三种做法：

| 做法 | 好处 | 主要问题 | 决定 |
|---|---|---|---|
| 在现有 V5 上继续加开关 | 改得快 | 旧代码和实验代码不断累积，最难读 | 不采用 |
| 在现有 V5 文件中逐段删除 | 文件名容易保持 | 很容易漏掉隐蔽兼容逻辑，删错后难证明行为没变 | 只用于小修，不作为本次主路线 |
| 从已确认的 V5 有效路径重新提取干净母版 | 边界最清楚，能真正去掉旧包袱 | 必须做旧新行为对照，初次工作量较大 | 采用 |

V5 母版优先保持已有稳定入口文件名，减少服务器脚本和调用方变化；文件内部只保留 V5 真正使用的路径。旧 checkpoint 的字段兼容不塞回母版，改放到母版外的一次性转换工具中。

## 5. 不可破坏的统一规则

1. 母版一旦冻结，只读、只引用，不能直接提交修改。
2. 每个实验必须记录母版编号、母版 Tag 和准确的 40 位提交号，三者必须互相对应。
3. 同一框架的所有实验默认互为兄弟，必须分别从同一母版开始，不能从另一个实验分支继续开。
4. 实验代码不能并回母版分支，也不能移动母版 Tag。
5. 调参、消融、确认实验永远不会直接产生新正式框架。
6. 创新实验只有在结果确认、代码瘦身、机器验证和审核都通过后，才可以注册成新的同级正式框架。
7. 正式框架之间只保留历史来源连线，不做目录嵌套。V2 指向 V1、V3 指向 V2、V5 指向 V3，但它们仍是同级框架。
8. 历史 `v1`、`v2`、`v3`、`v5` Tag 和旧 `Trial / Attempt` 原地保留，不移动、不改名、不删除、不伪造成新格式。
9. 历史缺失参数只能标为未知或 `legacy_summary_only`，不能凭印象补数。
10. 新实验不再用 `ATTEMPT-xxx` 作为人看的主名称；旧编号只能写入 `legacy_ref` 或运行映射列。

## 6. 最终结构

代码身份和实验账本分开管理：

```text
正式框架注册表
├─ FRAMEWORK-V1 ── MODEL-V1-TEMPLATE-V1
├─ FRAMEWORK-V2 ── MODEL-V2-TEMPLATE-V1
├─ FRAMEWORK-V3 ── MODEL-V3-TEMPLATE-V1
└─ FRAMEWORK-V5 ── MODEL-V5-TEMPLATE-V1

experiments/v5/
├─ framework.yaml                 # 框架身份和历史来源
├─ TEMPLATE.yaml                  # 当前母版编号、Tag、commit、状态
├─ VERSION.md
├─ MODULES.md
├─ EXPERIMENTS.md
├─ tune/
│  ├─ INDEX.md
│  └─ TUNE-001_xxx/
├─ ablation/
│  ├─ INDEX.md
│  └─ ABLATION-001_local_branch_effect/
├─ innovation/
│  ├─ INDEX.md
│  └─ INNOVATION-001_dynamic_routing/
└─ confirmation/
   ├─ INDEX.md
   └─ CONFIRM-001_xxx/
```

每个实验目录保持简单：

```text
ABLATION-001_local_branch_effect/
├─ README.md                    # 为什么做、只改什么、怎么判定
├─ EXPERIMENT.yaml              # 母版身份、分支、状态、旧记录映射
├─ PARAMETER_MATRIX.csv         # 每次运行的完整参数，机器读取
├─ PARAMETER_MATRIX.md          # 同一张表的人类阅读版
├─ result.md                    # 结论和证据入口
└─ evidence/                    # 小型审核和证据索引，不放大 checkpoint
```

实际训练日志、checkpoint 和大结果仍放外部实验存储，Git 里只保留哈希、路径、摘要和可复查入口。

## 7. 母版从产生到冻结

### 7.1 草稿阶段

先从该框架被接纳时的准确代码提交开始，只提取该框架真正启用的代码路径。这个阶段可以修改，但必须使用独立工作分支，状态为 `draft`。

### 7.2 对照阶段

用固定小输入、固定随机种子和固定配置，对比旧代码与新母版：

- 模型输出 `logits`；
- 训练损失各分量；
- 关键层梯度；
- 数据划分、类别顺序和标签映射；
- U、S、H、ZS 指标计算入口。

只有本来就应该相同的内容才要求数值一致。允许的差异必须逐条写清原因，不能用“代码清理过”笼统带过。

### 7.3 服务器确认阶段

本地行为对照通过后，再在服务器按冻结配置运行确认实验。服务器结果用于证明瘦身没有改变正式框架的实际能力，不用来顺便调新参数。

### 7.4 冻结阶段

机器验证、服务器确认和三轮有效审核全部通过后：

1. 把母版状态改为 `frozen`；
2. 记录准确 commit；
3. 创建不可移动的 `model/vX-template-vN` Tag；
4. 把母版登记到对应 `TEMPLATE.yaml`；
5. 工作流开始允许实验从该母版开分支；
6. 母版分支以后拒绝直接写入。

如果发现母版本身有缺陷，旧母版不改，建立新母版版本。旧实验继续指向旧母版，保证过去结果还能解释。

## 8. 一个新实验怎样开始

1. 先在所属框架的四类索引中创建实验项。
2. 读取该框架当前 `TEMPLATE.yaml`，得到母版编号、Tag 和 commit。
3. 从该准确 commit 创建实验分支，不能只凭一个可能移动的分支名。
4. 在实验的 `EXPERIMENT.yaml` 和参数表中写入同一组母版身份。
5. 预运行检查确认：工作区干净、当前提交确实来自指定母版、未混入别的实验提交。
6. 每次运行只在参数矩阵增加一行 `RUN-xxx`，不额外制造一个新 Attempt 目录。
7. 结果写回实验账本和证据索引，实验代码保留在自己的分支，不回写母版。

工作流遇到以下情况必须拒绝启动服务器任务：

- 母版编号、Tag、commit 对不上；
- 实验分支不是从登记的母版提交开始；
- 母版工作区有直接修改；
- 参数表没有准确记录本次改动；
- 试图从另一个实验分支继续开工，却没有用户明确批准的组合实验说明。

确实需要组合两个已验证实验时，必须新建一个独立创新实验，从母版重新实现两个动作并设置组合对照，不能直接拿两个旧实验分支随手合并。

## 9. 创新怎样变成新框架

```text
FRAMEWORK-V5 的干净母版
        │
        ├─ V5-INNOVATION-001（候选，无正式 Tag）
        │          │
        │          └─ 结果确认 + 代码清理 + 审核通过
        │
        └──────────────> FRAMEWORK-V6（新的同级框架）
                          ├─ MODEL-V6-TEMPLATE-V1
                          ├─ tune
                          ├─ ablation
                          ├─ innovation
                          └─ confirmation
```

V6 的 `derived_from_framework` 指向 V5，`promoted_from_experiment` 指向 `V5-INNOVATION-001`。V6 不放进 V5 目录，V5 母版也不因为 V6 出现而改变。

## 10. 现有框架和实验怎样迁移

### 10.1 V1、V2、V3、V5

四个正式框架都补上母版登记信息。迁移分两层：

- 历史身份层：现有正式 Tag 和 commit 先登记为 `legacy_frozen`，说明它能回查历史，但还没有经过本次干净母版重建。
- 干净母版层：先完成仍要继续做实验的 V5，再按 V3、V2、V1 的顺序处理。每完成一个，就新增自己的 `MODEL-VX-TEMPLATE-V1`，不覆盖历史 Tag。

这样不会假装旧框架已经被清理，也不会因为等待全部旧框架重建而阻塞当前 V5 实验。

### 10.2 现有四类实验

现有正式实验目录补上 `EXPERIMENT.yaml` 和母版身份字段。已经发生的历史实验继续引用当时真实的代码 Tag/commit；不能把旧结果倒填成从未来的干净母版运行。

只处于计划状态、尚未实际训练的实验，改为从当前可用的干净母版重新起步。已经运行的实验只补索引和映射，不重写结果。

### 10.3 Trial、Attempt 和 DR

旧目录原地只读保留：

```text
旧 ATTEMPT-019
  └─ legacy_ref ──> V5-ABLATION-001

ATTEMPT-019 里的多个 DR 任务
  └─ 可证明的逐任务记录 ──> PARAMETER_MATRIX 中的 RUN-001...RUN-N
```

能证明的参数、种子、commit 和结果逐行映射；不能证明的内容标为未知。旧目录不再继续新增正式运行。

## 11. V5 终极瘦身边界

V5 干净母版只保留 V5 正式方法实际需要的能力：

- PSE；
- FGVD；
- conditional BVSA 文本路径；
- ICSA；
- SGMP；
- 局部与全局的固定融合；
- 当前正式训练、验证和评估流程。

明确移出 V5 母版：

- V1/V2/V3 遗留但 V5 不再使用的实现；
- 同一个配置含义的多套旧名称和兼容别名；
- 只为读取旧 checkpoint 保留的占位字段；
- 已经废弃的训练入口和不可达分支；
- 动态路由等后续创新实验代码；
- 只为某次调参或消融增加的永久开关；
- 没有实际调用方的参数、类和辅助函数。

旧 checkpoint 如需继续使用，由母版外的转换工具一次性改成新母版格式。转换必须保留输入文件、输出文件、字段映射、哈希和验证结果，不能静默改写原 checkpoint。

V5 瘦身不以“必须减少某个百分比”为验收标准；以行为保持、边界清楚、无废弃路径和后续实验不再继续堆开关为准。行数和配置项减少量会记录，用来说明可读性改善，但不能凌驾于正确性。

## 12. 工作流和数据需要增加什么

### 12.1 框架母版账本

新增 `TEMPLATE.yaml`，至少记录：

```yaml
schema_version: gtpj.framework_template.v1
framework_id: FRAMEWORK-V5
template_id: MODEL-V5-TEMPLATE-V1
template_status: draft | confirmed | frozen | retired | legacy_frozen
template_branch: framework/v5-template-v1
template_tag: model/v5-template-v1
template_commit: 40位提交号
source_framework_tag: v5
source_framework_commit: 40位提交号
behavior_contract: docs/workflow/contracts/v5_behavior_contract.md
```

### 12.2 实验身份账本

每个实验新增 `EXPERIMENT.yaml`，至少记录：

```yaml
schema_version: gtpj.experiment.v1
experiment_id: V5-ABLATION-001
framework_id: FRAMEWORK-V5
kind: ablation
base_template_id: MODEL-V5-TEMPLATE-V1
base_template_tag: model/v5-template-v1
base_template_commit: 40位提交号
experiment_branch: exp/v5/ablation/v5-ablation-001-local-branch-effect
status: planned
legacy_ref: ATTEMPT-019 的真实路径或 none
```

### 12.3 自动检查

需要增加并纳入现有统一校验入口：

- 母版 schema 校验；
- 实验 schema 校验；
- 母版 Tag 与 commit 一致性校验；
- 实验分支基点校验；
- 四类索引与实验目录双向一致性校验；
- 旧记录映射不伪造校验；
- 禁止把实验提交写回母版的边界检查；
- 生成式 `EXPERIMENTS.md` 和总注册页面刷新检查。

## 13. 完成标准

### 13.1 结构正确

- V1、V2、V3、V5 都有明确的母版身份记录；
- 所有现有正式实验都有母版或真实历史基点记录；
- 四类实验仍然同级，正式框架仍然同级；
- 历史目录和 Tag 数量没有被减少或改写；
- 新实验无法绕过母版检查启动。

### 13.2 V5 行为正确

- 固定小输入下，旧 V5 有效路径和新母版的输出、损失和关键梯度在约定误差内一致；
- 数据划分、类别顺序、标签映射、logits 形状和 U/S/H/ZS 计算语义不变；
- 局部分支、全局分支和固定融合仍是 V5 本身的一部分；
- 动态路由和其他候选创新不在母版中；
- 服务器确认结果达到事先写明的等价边界，失败时不冻结。

### 13.3 可读性改善

- V5 不再保留无调用方的旧类、旧配置别名和废弃分支；
- 配置文件只出现 V5 当前真实参数；
- 一个新实验只需要看 `README.md`、`EXPERIMENT.yaml`、参数表和结果页；
- 记录瘦身前后的文件行数、配置键数量和分支数量，作为可读性证据。

### 13.4 审核和验证

这是会改变代码组织、训练入口和实验结论解释方式的大改，按三轮有效审核处理：

1. 第一轮检查规范、数据结构和迁移是否会丢历史；
2. 第二轮检查 V5 新旧代码行为、训练和评估语义；
3. 第三轮检查服务器证据、最终差异和是否可以冻结。

任何超时、报错或空输出都不算审核轮次。机器测试、schema 检查和真实小样例不能被人工审核替代。

## 14. 失败预演和回退

| 可能失败 | 怎么提前发现 | 怎么处理 |
|---|---|---|
| 新母版不小心改变 V5 数学行为 | 固定输入对比输出、损失和梯度 | 不冻结，继续修；正式 `v5` Tag 不动 |
| 实验从错的代码起点开始 | 启动前核对母版 Tag、commit 和 merge-base | 直接拒绝运行，重新从正确母版开分支 |
| 旧实验被误写成新母版结果 | 检查运行日期、commit 和 legacy_ref | 保留真实历史基点，不倒填未来母版 |
| checkpoint 因字段清理无法加载 | 转换工具做字段清单、哈希和最小推理 | 保留原文件，转换失败就继续用旧代码回查 |
| 创新代码污染 V5 母版 | 检查母版分支写入和提交来源 | 阻止合并；创新留在自己的实验分支 |
| 四类台账和目录不一致 | 双向索引校验和生成页差异检查 | 校验失败，不允许进入 Runner |

回退始终以原正式 Tag 和准确 commit 为锚点。此次迁移不删除历史、不移动旧 Tag、不重写 Git 历史，因此设计本身允许逐框架撤回。

## 15. 证据、决定和仍需实测的内容

### 已核实事实

- 现有正式框架为 V1、V2、V3、V5，文件系统和注册关系已经平级。
- V2 来源指向 V1，V3 指向 V2，V5 指向 V3。
- 每个正式框架已经有调参、消融、创新、确认四类账本。
- V5 当前代码由 V3 演变而来，现有代码和后续实验代码存在继续叠加的风险。
- 旧 Trial/Attempt 保存了需要继续回查的实验事实，不能删除。

### 用户已经明确决定

- 每个正式框架必须有永远不被实验直接修改的模板代码。
- 同一框架的每个实验都从干净模板独立加工一次。
- 创新成功后成为新的同级框架，不嵌套在旧框架内部。
- 现在的实验也要迁入同一套清楚、可读的统一规范。

### 必须通过实施阶段实测，不能现在假定

- V5 新旧代码逐项数值等价的误差范围；
- 服务器确认需要多少次重复才能满足稳定性；
- 每个历史实验是否都能恢复完整逐运行参数；
- V1、V2、V3 清理时各自能删除多少旧代码。

这些未知项不会阻止先建立规范和账本，但会阻止对应母版被标为 `frozen`。

## 16. 本次不做的事

- 不删除或改名旧 Trial、Attempt、DR、checkpoint、日志和历史 Tag；
- 不自动 push、发布或部署；
- 不在母版确认前宣称 V5 精度不变；
- 不把动态路由或局部分支消融结果提前写成正式结论；
- 不在没有证据时补猜历史参数；
- 不因为整理结构就自动把任何创新晋级为新框架。

## 17. 签署规则

> 本设计通过后，GTPJ 统一采用“一个正式框架对应一套可版本化的只读代码母版；四类实验从准确母版提交独立分叉；实验不回写母版；创新确认后才建立新的同级正式框架”的规则。现有和未来实验都遵守同一规则，历史证据原地只读保留。
